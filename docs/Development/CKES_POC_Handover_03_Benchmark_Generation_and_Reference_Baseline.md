# CKES POC Handover 03: Benchmark Generation and Reference Baseline

## Instructions to Cursor Plan

This is **Handover 3 of 3**. Begin planning only after Handover 2 has been built, validated, and architect-accepted.

Create one plan for qualification, import, execution, and evidence capture. Do not ask the architect to manually author the scenario corpus. Do not build or run the plan until it has been externally reviewed, amended, architect-approved, and explicitly authorized.

The actual benchmark JSON packs will be generated externally against the finalized Handover 1 schema. Cursor must not silently change their expected results. Schema or semantic defects must be reported for correction.

Apply current EDF requirements. Do not create CKES-0001; this stage produces POC evidence for the future human promotion gate.

## Outcome

Generate, qualify, freeze, import, and execute versioned Anchor, Statistical, and Challenge benchmark packs; capture the current CKES POC as Reference Baseline 001; and produce defensible evidence for future architectural decisions.

## Benchmark releases

Prepare releases equivalent to:

- `CKES-BENCHMARK-ANCHOR-001`
- `CKES-BENCHMARK-STATISTICAL-001`
- `CKES-BENCHMARK-CHALLENGE-001`

The exact artifact names must follow the finalized schema and repository conventions.

### Anchor suite

Approximately 50–100 clear, interpretable, architecturally important cases. Cover all primary decision classes, dangerous false merges, applicability, objective/method distinctions, ambiguity, and at least two materially different domains.

### Statistical suite

Approximately 500–2,000 controlled synthetic cases. Use declared semantic transformations so expected outcomes follow from construction wherever possible.

### Challenge suite

Approximately 100–500 difficult, ambiguous, adversarial, compound, boundary, and revalidation cases. Correct deferral is often the expected behavior.

Initial releases may be smaller if cost or POC maturity requires it, but the plan must state what statistical claims are and are not justified by the sample size.

## Controlled generation taxonomy

Packs should cover transformations including:

- paraphrase same identity;
- terminology substitution same identity;
- narrow/broaden applicability;
- change subject/object/context;
- objective-to-method and method-to-objective;
- supporting observation;
- contradiction;
- qualification;
- related but distinct;
- compound assertion;
- genuinely novel;
- irrelevant near-neighbor;
- adversarial false-merge candidate;
- emerging-process/revalidation signal.

Record generation provenance and transformation for evaluation, but never expose it to the tested pipeline.

## Domain coverage

Do not promote evidence from culinary cases alone. Include at least:

- culinary/TRV/CALS cases; and
- a materially different structured engineering domain such as electronics/ELS.

Additional domains are desirable when they test terminology collisions or different applicability models.

## Qualification and review

The architect is not expected to label every case. Qualification should include:

- automated schema and integrity validation;
- duplicate and contradiction checks within packs;
- consistency checks between transformation and expected outcome;
- independent AI review where practical;
- stratified human spot review;
- mandatory review of high-severity and false-merge cases;
- disputed-label workflow;
- pack-level and scenario-level review status.

AI-generated labels must use the confidence classes from Handover 1. Ambiguous cases should often expect deferral or allow an acceptable result set rather than inventing false certainty.

Where practical, do not evaluate a model solely on cases generated by the same model/prompt family.

## Freeze and version

Once qualified:

- freeze JSON content;
- generate deterministic hashes;
- generate derived Markdown;
- record schema/harness compatibility;
- prohibit mutation during scored runs;
- require new versions for corrections or additions.

## Reference Baseline 001

Capture the current CKES POC before the proposed economical mechanisms are implemented, or document precisely which mechanisms already exist.

Run the same frozen packs under recorded profiles:

- clean-state reference run;
- warm-state run only where reusable prior decisions are intentionally seeded;
- repeated trials for LLM-dependent cases as budget permits.

Record all run-configuration details and limitations. Never compare unmatched pack versions as if they were equivalent.

## Baseline metrics

Report at least:

- same-identity accuracy;
- related-distinct accuracy;
- novel-candidate accuracy;
- correct-deferral rate;
- false-merge rate;
- missed-match rate;
- applicability accuracy;
- objective/method accuracy;
- contradiction/revalidation accuracy;
- results by domain and confidence class;
- LLM calls, tokens, cost, and latency;
- prior-decision reuse;
- human-review demand;
- infrastructure failure rate;
- stability across repeated trials.

Do not claim improvement from pass rate alone if false merges, cost, or instability worsens.

## Baseline anchors

If the repository uses the phrase “baseline anchors,” define it as the fixed run conditions and metrics required for reproducibility—not as a synonym for the Anchor Benchmark Suite.

## Comparative experiment protocol

Document how later CKES changes will be compared with Reference Baseline 001:

1. use identical frozen benchmark pack versions;
2. record changed code/config/model components;
3. execute comparable clean/warm profiles;
4. quantify accuracy, safety, cost, latency, and stability deltas;
5. investigate all new high-severity failures;
6. disclose non-comparable conditions;
7. never tune against a hidden challenge/holdout subset and then report it as unseen evidence.

Consider maintaining a held-out challenge subset for later evaluation.

## Evidence and governance

Update the appropriate POC findings, provisional-requirement matrix, ADR/AAR evidence, and integration reports with:

- exact packs and hashes;
- environment and configuration;
- results and confidence;
- mocked/unimplemented capabilities;
- limitations and invalid claims;
- failures and remediation work;
- whether evidence is sufficient for each CKES-PAR item.

A green benchmark does not automatically promote CKES-PAR requirements or authorize CKES-0001. Promotion remains a separate human architectural decision under ADR-0001.

## Data-quality and security controls

- Use fictitious or approved synthetic data.
- Do not include secrets, personal data, or copyrighted corpora beyond allowed use.
- Guard generated source text against prompt injection affecting the harness.
- Ensure expected fields never enter the tested prompt.
- Keep benchmark execution out of production canonical state.

## Out of scope

- Production application integration.
- Automatic CKES-0001 creation.
- Automatic acceptance of every AI-generated label.
- Claiming real-world prevalence from synthetic distributions.
- Replacing future real-source validation with synthetic testing alone.

## Acceptance criteria for Handover 3

- Three versioned JSON suite classes are produced and schema-valid.
- Packs are qualified, frozen, hashed, and rendered to Markdown.
- At least two materially different domains are covered.
- High-severity cases receive explicit review.
- Reference Baseline 001 is a selected run, not a suite.
- Clean/warm configuration and LLM trial counts are recorded.
- Accuracy, safety, routing, cost, latency, reuse, and stability metrics are reported.
- Expected-result leakage is excluded.
- Evidence limitations are documented.
- POC/AAR/matrix documents reference exact artifacts and hashes.
- No CKES-0001 is created automatically.
